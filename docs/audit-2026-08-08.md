## H1 — Pipeline mutual exclusion is host-local, but the database is shared

**Confirmed.** `tryAcquirePipelineLock` ([pipelineState.ts:105](../src/lib/pipelineState.ts:105))
takes a lock on the **local filesystem**. Both this Mac and the Pi run the app
against the *same* Postgres. Neither host can see the other's lock.

Evidence taken during the audit:

| | value |
|---|---|
| Mac `data/runtime/pipeline-state.json` | `isRunning: false`, "Pipeline manually stopped" |
| Shared DB `PipelineState` row | `isRunning: true`, `Searching ATS Boards: [895/13022]`, updated **3s ago** |
| Lock file on this Mac | **none present** |

The Pi is mid-run; the Mac holds no lock. A `POST /api/pipeline/run` on the Mac
would acquire its (absent) local lock and start a **second concurrent pipeline**
against the same database.

Consequences: duplicated ingestion work, doubled consumption of paid API quota
(see H2), and racing writes to the same job rows.

**Fix sketch:** move the lock into the database — a row with an owner token and
heartbeat, claimed by conditional update, exactly like the `NativeScoringRequest`
lease pattern already in the codebase. That pattern is proven here and would make
the lock meaningful across hosts.

## H2 — "Stop Pipeline" cannot stop a pipeline running on the other host

**Confirmed by code path.** The run loop's exit check is
`if (ac.signal.aborted || !readPipelineState().isRunning) break;`
([run/route.ts:119](../src/app/api/pipeline/run/route.ts:119)), and
`readPipelineState()` reads the **local file**.

Pressing Stop on the Mac writes `isRunning: false` to the Mac's file and mirrors
it to the shared DB, so the banner goes quiet — but the Pi's loop only ever
consults *its own* file and keeps going. The banner flips back on the Pi's next
tick.

This is the most likely explanation for a Stop that "doesn't take".

**Fix sketch:** falls out of H1 — once the authoritative state is the shared DB
row, both the exit check and the button act on the same record.

## H3 — Every paid ingestion source has been failing for ~11 days, silently

**Confirmed.** Last successful Indeed run: **2026-07-28**. Failed runs in the last
7 days:

| source | failures | latest error |
|---|---|---|
| Indeed | 224 | All configured API keys are exhausted or missing |
| SerpApi | 188 | operation aborted due to timeout |
| JSearch | 132 | **HTTP 404** |
| LinkedIn | 132 | **HTTP 404** |
| Glassdoor (RapidAPI) | 126 | All configured API keys are exhausted or missing |
| Adzuna | 21 | HTTP 503 |

Keys *are* present in `.env` (`RAPIDAPI_KEYS` is 509 chars, `SERPAPI_KEY` 64), so
this is quota exhaustion or expiry rather than missing configuration. The two
`HTTP 404`s are a different failure — a 404 from an API endpoint usually means the
route moved, not that the query found nothing.

Nothing surfaces this. `IngestionSourceRun` records every failure faithfully, but
no view reads it, so the pipeline reports "Active" while its paid sources return
nothing for a week and a half.

**Fix sketch:** surface per-source health (last success, consecutive failures) on
the Stats or Log tab. The telemetry already exists; only the display is missing.

## M1 — 40% of ATS boards are blacklisted, and the queue is far behind

**Confirmed.**

```
active 41,305 | parked 5,589 | blacklisted 31,234   (78,128 total)
boards due for a check right now: 27,486
```

Blacklisting is recoverable — the selection query does include `blacklisted` and
retries after 30 days — so this is not a deadlock. The concern is throughput and
signal: the run processes boards in 6 chunks, one chunk per pass
([run/route.ts:119](../src/app/api/pipeline/run/route.ts:119)), against a 27k
backlog. And a 40% blacklist rate suggests many boards are failing for a
systematic reason worth investigating rather than aging out one at a time.

## M2 — `scoringStatus: 'failed'` has no retry path

**Confirmed.** 553 rows. Nothing selects `failed` for reprocessing — local scoring
only ever selects `queued`. The `isDead` branch also sets `status: 'dismissed'`,
so 503 of these are dismissed and out of sight.

Of the 553, **26 now have a description that passes the current quality gate**.
The requeue script added today only recovers those carrying the gate's own pass
reason; the rest failed via Jina ("Jina could not parse JD", 497 rows) and stay
parked.

**Fix sketch:** decide deliberately whether Jina failures deserve a retry sweep.
They may legitimately be dead links — worth sampling 10 before building anything.

## M3 — The pipeline-state mirror to the database is fire-and-forget

**Confirmed by code.** `updatePipelineState` writes the file synchronously, then
mirrors to Postgres with `.catch(err => console.error(...))`
([pipelineState.ts:59](../src/lib/pipelineState.ts:59)). The status route reads
**DB first**, file only as fallback.

So a failed mirror — and this database went unreachable for two days this
week — leaves the dashboard showing stale pipeline state indefinitely, with the
only trace in server logs.

## L2 — Seven `[id]` routes accept an unvalidated id

**Confirmed.** `jobs/[id]`, `jobs/[id]/pass`, `jobs/[id]/promote`,
`jobs/[id]/scrape`, `jobs/[id]/redirect`, `outreach/[id]`,
`outreach/[id]/generate` pass the path segment straight to Prisma. The newer
scoring routes validate with `UUID_PATTERN`.

Not injectable — Prisma parameterizes — so this is consistency and error quality
(a malformed id produces a confusing 500 rather than a 400), not a vulnerability.

## L3 — Unbounded `findMany` on rows carrying full descriptions

**Suspected.** [cooldownRecovery.ts:9](../src/lib/cooldownRecovery.ts:9) selects
every `cooldown` job with no `take` and no `select`, pulling whole rows including
`description`. That is 975 rows today — fine now, unbounded by construction, and
it runs on a Raspberry Pi. Adding `select` for the needed columns is cheap
insurance. Other unbounded queries I checked are over genuinely small sets
(`inbox` = 52).

## L4 — Inline styles defeat the responsive stylesheet

**Confirmed pattern** (two instances fixed today). Inline `style={{…}}` beats any
stylesheet rule, so media-query overrides written against those elements are dead
on arrival — the expand footer had a `padding: 15px 20px` mobile rule that had
never once applied. `ExpandOverlay.tsx` and `Dashboard.tsx` carry dozens more.

Not worth a sweep; worth knowing when a responsive rule "doesn't work".
